# Automation Knowledge Engine — Architecture Gap Report

Date: 2026-07-16  
Status: Architecture review only; no implementation authorized or performed

## Executive conclusion

The design vision is directionally correct, but the application is not starting from zero. It already has a platform-neutral workflow, strict schemas, provider-independent compilation, graph validation, schema repair, platform adapters, synchronized canvas/sidebar projections, versioned persistence, and three workflow views.

The next phase should therefore **extend the existing shared and platform packages**, not create a second `workflowKnowledge` architecture beside them. The most important missing capability is a grounded planning layer between the user’s scope and Qwen:

`scope → deterministic fact extraction → relevant knowledge retrieval → capability-constrained planning → semantic validation → deterministic repair → targeted AI repair → platform projection`

The recommended plan is 9 small sprints. The first 6 create the intelligence foundation; the last 3 integrate it with platform mapping, views, and observability. Implementation should not begin until this plan is approved.

## 1. Current workflow generation flow

```text
Scope text or extracted document
  → project scope persisted in SQLite
  → POST /api/workflows/analyze
  → AnalysisService
  → selected provider (Ollama, OpenAI, or deterministic local fallback)
  → one static workflow-analysis prompt + full canonical JSON schema
  → JSON extraction/repair
  → strict Zod schema validation
  → structural candidate repair (IDs, nulls, misplaced properties)
  → infer sequential connections when no topology exists
  → architecture compiler
       • enrich node guidance
       • insert convergence merges
       • ensure decision exits
       • add retry metadata to external actions
       • add terminal End nodes
  → graph validation
  → fallback to deterministic local provider when model output is unacceptable
  → persist canonical workflow + projected visual graph + immutable project version
  → platform build plan generated on demand
  → React Flow canvas, business view, implementation view, validation, and exports
```

The pipeline is clean at the service boundary but shallow before model invocation. Qwen receives the scope, target platform, a general system prompt, and the complete schema. It does not receive retrieved node manuals, matched patterns, operation constraints, detected cardinality, or a capability allowlist.

## 3. Current strengths

1. **Correct domain direction.** Canonical workflow data is independent of Zapier, Make, and n8n.
2. **Strong runtime boundaries.** Strict Zod parsing prevents malformed model output from entering persistence.
3. **Provider isolation.** Ollama is serialized for local hardware, supports ordered local-model fallback, and never silently fails over to a paid cloud provider.
4. **Single-source UI projections.** Canvas, sidebar, validation, platform recommendations, and exports derive from canonical records.
5. **Graph safety.** Duplicate IDs, dangling edges, invalid cycles, incomplete decisions, and invalid merges are detected.
6. **Migration safety.** Schema v1/v2 migration and project versions reduce rollout risk.
7. **Existing platform seam.** `packages/platforms` is the correct place to extend capability-aware mapping.
8. **Useful compiler seam.** The architecture compiler already demonstrates provider-independent deterministic enrichment.
9. **Local-first operation.** The current structure is appropriate for Qwen and constrained hardware.
10. **Meaningful tests already exist.** Providers, repair, graph integrity, compiler behavior, adapters, services, documents, and UI have baseline coverage.

## 4. Current weaknesses

### Planning is under-grounded

The prompt asks Qwen to consider many architectural concerns but supplies no retrieved domain knowledge. Correctness depends too heavily on the model already knowing each automation concept and application operation.

### The node taxonomy is inconsistent

Current `category` values mix canonical control-flow types (`condition`, `loop`, `merge`) with application domains (`crm`, `email`, `database`) and UI helpers (`note`, `group`). The proposed design correctly separates canonical behavior from application category, but a hard replacement would break stored workflows. A compatibility mapping is required.

Missing first-class semantics include:

- data retrieval
- validation
- iterator distinct from loop
- aggregator
- manual review distinct from human approval
- explicit canonical binary condition and multi-route decision names

### Platform mapping is too category-driven

Examples:

- Every current `condition` aliases to `filter`, even when the false path has meaningful work.
- Make binary conditions need a Router with two filters, not a generic filter.
- Zapier needs Filter only for stop-on-false behavior; otherwise Paths.
- Loop, iterator, and aggregator are collapsed into broad catalog entries.
- Mapping results do not store confidence or alternatives as formal fields.

### Compiler repairs can invent meaning

`enforceConditionBranches` adds terminal branches even when the correct missing outcome is unknown. `insertExplicitMerges` inserts a merge for any node with multiple incoming edges, even though exclusive branch convergence and parallel synchronization have different semantics. These should become validation findings followed by confidence-gated repair.

### Validation is structurally stronger than semantically strong

The engine cannot currently prove:

- that an iterator receives a collection
- that a single-item operation is inside an iterator
- that a loop has a real counter/timeout and exit rule
- that route values are exhaustive or distinct beyond edge labels
- that a delay has duration/timezone/resume behavior
- that a merge is valid for the branch semantics
- that an application operation actually exists

### Repair is schema-oriented, not issue-oriented

Current repair fixes IDs, nulls, and schema defaults. It does not consume structured validation issues, apply ordered graph transformations, keep a repair log, cap attempts, or revalidate after each semantic repair stage.

### One project cannot represent several workflows

The Asana example is five automations. The current project model stores one workflow JSON and one visual graph JSON. Treating five automations as one disconnected or loosely connected graph causes the exact ambiguity seen in earlier samples.

### Layered views are projections, but not graph-aware projections

The Business View filters technical node categories then renders nodes in array order, which can misrepresent branches. The Implementation Notes view is documentation, not a Developer View with technical nodes and edges. Visibility metadata does not yet exist.

## 6. Conflicts and recommended deviations from the vision

### Do not create dozens of one-file manuals immediately

The proposed folder tree is illustrative but too fragmented for the current TypeScript monorepo. Separate files for every manual, validator, and schema would increase navigation cost without improving runtime separation.

Prefer cohesive packages:

```text
packages/knowledge/
  src/registry/
  src/applications/
  src/patterns/
  src/retrieval/
  src/index.ts

packages/shared/src/
  knowledge-context.ts
  planning-facts.ts
  semantic-validation.ts
  workflow-repair.ts
```

Split a file only when its data or behavior becomes large enough to justify it.

### Do not encode manuals as long prose sent to the model

Manuals should be typed facts: preconditions, incompatible uses, required configuration, accepted cardinality, output cardinality, validation rule IDs, and concise prompt guidance. Long prose is harder to validate, retrieve, version, and test.

### Do not use vector search yet

The initial knowledge base is small and structured. Deterministic token/entity matching plus weighted pattern rules will be faster, inspectable, dependency-free, and more reliable locally. Add embeddings only when the catalog becomes too large for structured retrieval.

### Do not let the compiler silently invent business branches

Safe structural repairs may be automatic. Missing business outcomes should be a clarification or targeted repair unless a matched pattern supplies an explicit fallback with high confidence.

### Separate iterator from loop in semantics, not only labels

An iterator transforms collection cardinality into per-item execution. A loop repeats a sequence under a termination rule. They need different configurations and validators even if a target platform implements both with related primitives.

### Preserve one canonical graph, but allow a project to contain several graphs

The best model is `Project → WorkflowSet → CanonicalWorkflow[]`, not one mega-graph and not separate platform graphs. Each automation remains independently valid, editable, mappable, and exportable.

### Developer View should be derived, not stored as a second workflow

Add visibility and concern metadata to canonical nodes/edges. A projection service selects and contracts nodes for each view. Technical safeguards may be explicit canonical nodes when real, but hidden outside Developer View.

## 7. Target architecture

```text
Requirements
  ↓
Scope Analyzer
  produces PlanningFacts + evidence + uncertainties
  ↓
Knowledge Retriever
  selects node definitions + operation capabilities + patterns + platform constraints
  ↓
Planning Context Builder
  creates compact, inspectable, versioned context
  ↓
AI Planner
  returns WorkflowSet candidate using allowed capabilities only
  ↓
Schema Boundary
  parses and normalizes shape
  ↓
Semantic Validator
  produces structured issues with suggested repair IDs
  ↓
Deterministic Repair Engine
  applies safe, ordered, logged transformations
  ↓ invalid ambiguity remains
Targeted AI Repair
  edits only affected workflow fragments; bounded attempts
  ↓
Revalidation
  ↓
Platform Projection
  mapping + confidence + limitations + alternatives
  ↓
View Projection
  Business / Automation / Developer
  ↓
Branch-aware Layout + Canvas + Exports
```

Core rule: every intermediate artifact should be schema-bound, inspectable in development, and independently testable.

| Pattern matcher | Medium | Weighted rules are straightforward; avoiding overmatching requires fixtures. |

| Deterministic repair | High | Incorrect automatic repair can corrupt business meaning. |
| Targeted AI repair | Medium–High | Requires bounded patch schema, issue scoping, and idempotent revalidation. |

Overall: approximately 9 focused sprints, likely 5–9 engineering weeks for one experienced full-stack engineer depending on knowledge-pack depth and UI polish. Local Qwen variability is the largest uncertainty.

## 11. Migration risks

1. **Taxonomy migration:** changing `category` directly would invalidate stored JSON. Introduce `canonicalType` while retaining `category` as a compatibility alias for one schema version, then migrate.
2. **Multi-workflow migration:** wrap every existing project workflow in a one-item workflow set without changing workflow/node/edge IDs.
3. **Visual graph migration:** visual positions must become workflow-scoped. Stale visual IDs must be ignored safely, as the editor now does.
4. **Platform mapping drift:** saved canonical workflows must not store derived platform nodes. Recompute mappings under a versioned catalog.
5. **Repair behavior change:** stricter validation may make older workflows appear invalid. Validation versions and legacy warnings are safer than destructive auto-repair.
6. **Prompt/schema size:** adding all knowledge to the schema or prompt can exceed local context and slow Qwen. Retrieval and token budgets are mandatory.
7. **Pattern overreach:** aggressive matching can insert irrelevant control flow. Store scores and reasons; require thresholds.
8. **Database rollback:** SQLite `ALTER TABLE` limitations require additive migrations and backups/version snapshots before conversion.
9. **UI compatibility:** existing editor commands assume one workflow and broad categories. Introduce selectors and adapters before removing old fields.

## 12. Technical debt observations

- `domain.ts` is becoming a large mixed-concern schema file.
- Node `category` conflates control behavior and application domain.
- The `branches` collection duplicates information already present in connections and can drift.
- Routine editor-created edges are still labeled `SUCCESS`, while migration/compiler semantics prefer unlabeled routine flow.
- Platform service/event matching relies heavily on strings and first-match word overlap.
- The deterministic local provider contains hard-coded scenario behavior and line-oriented heuristics.
- Analysis fallback replaces the entire model result instead of preserving valid portions.
- `AnalysisService` owns orchestration, fallback, parsing, compilation, validation, and persistence; it will become too large without explicit pipeline stages.
- Business View uses node array order rather than a topological graph projection.
- Implementation Notes is mislabeled as the third workflow layer; it lacks technical topology.
- The compiler mutates node objects during enrichment, making pure transformation tests harder.
- Some generated guidance is generic and repeated rather than registry-grounded.
- Test coverage is good for current foundations but sparse for editor behavior and absent for semantic planning.

## 13. Recommended implementation sprints

### Sprint K1 — Planning contracts and observability

**Goal:** Define the intermediate artifacts before adding intelligence.

**Architecture changes:** Add `PlanningFacts`, evidence, uncertainty, retrieval result, validation issue, repair action/report, mapping confidence, and workflow-set schemas. Keep all current behavior behind adapters.

**Files:** New shared schema files; exports from `packages/shared/src/index.ts`; schema fixtures/tests.

**Tests:** Strict parsing, backward compatibility, unknown-field rejection, evidence references, one-workflow migration into a workflow set.

**Expected output:** Stable contracts that every later stage can consume independently.

**Rollback risk:** Low. New types can remain unused; no persistence migration yet.

### Sprint K2 — Canonical knowledge registry and operation packs

**Goal:** Establish grounded, typed automation knowledge.

**Architecture changes:** Create `packages/knowledge`; define canonical functions and initial Asana, Google Drive, Google Sheets, Gmail, Slack, Webhook/API, and generic CRM operations. Reuse and gradually replace the current application registry.

**Files:** New knowledge package; minor shared/platform exports; registry tests.

**Tests:** Unique IDs, valid operation references, cardinality declarations, unsupported-operation behavior, platform limitation presence.

**Expected output:** Queryable canonical definitions and operation capabilities without involving AI.

**Rollback risk:** Low. Existing application registry remains the active fallback.

### Sprint K3 — Scope facts and deterministic retrieval

**Goal:** Convert scope prose into inspectable planning facts and retrieve only relevant knowledge.

**Architecture changes:** Add application/entity/business-verb/decision/cardinality detectors, weighted pattern matcher, and compact retriever. Start with deterministic lexical rules and curated synonyms—no embeddings.

**Files:** Server analysis modules; knowledge patterns/retrieval; fixtures.

**Tests:** Collection vs single detection, binary vs multi-route detection, follow-up loop match, create-or-update match, false-positive controls, retrieval size budget.

**Expected output:** A development-inspectable context containing matched facts, patterns, operations, manuals, scores, and reasons.

**Rollback risk:** Low–Medium. Retrieval can run in shadow mode without changing generated workflows.

### Sprint K4 — Grounded prompt pipeline

**Goal:** Make Qwen plan only with retrieved and allowed capabilities.

**Architecture changes:** Split `AnalysisService` into pipeline stages; version the prompt context; include compact retrieved knowledge, facts, capability allowlist, and hard rules. Preserve current provider and deterministic fallback behavior.

**Files:** Analysis service, prompt builder, providers, new planner/context modules.

**Tests:** Prompt excludes irrelevant packs, respects token/size limits, preserves untrusted-scope boundaries, and contains allowed operations and detected facts.

**Expected output:** More specific nodes and operations with a recorded context trace.

**Rollback risk:** Medium. Local model output can regress; retain feature flag and current prompt.

### Sprint K5 — Semantic validation

**Goal:** Detect logically invalid but schema-valid workflows.

**Architecture changes:** Add validators for canonical type compatibility, binary/multi-route decisions, cardinality, iterator, loop termination, delays, merges, aggregators, operation support, and layered visibility.

**Files:** New shared semantic validation module; integration into `validateWorkflow`; validation panel updates.

**Tests:** All 12 required specification scenarios that concern validation, including collection-to-single-operation and unsupported mappings.

**Expected output:** Structured issue codes with node/edge IDs, explanations, and proposed repair IDs.

**Rollback risk:** Medium. Older workflows may surface new errors; initially classify compatibility findings as warnings.

### Sprint K6 — Safe deterministic and targeted AI repair

**Goal:** Repair obvious structural/semantic defects without regenerating correct work.

**Architecture changes:** Pure ordered repair rules, repair log, confidence gates, maximum attempts, fragment-based AI patch schema, revalidation after every pass.

**Files:** New semantic repair module, repair orchestrator, repair prompt, analysis integration.

**Tests:** Iterator insert/remove, IF/router conversion, duplicate edge removal, missing End repair, bounded loop repair, ambiguous branch refusal, idempotent second pass.

**Expected output:** Validated workflow plus transparent repair report; ambiguous business meaning becomes clarification rather than invention.

**Rollback risk:** High. Keep repairs previewable/logged and feature-flagged; never mutate the persisted prior version in place.

### Sprint K7 — Capability-aware platform mapping

**Goal:** Produce materially different, honest Zapier/Make/n8n implementation plans.

**Architecture changes:** Map by canonical type + operation capability + branch semantics, not broad category. Add confidence, limitations, alternatives, and catalog version.

**Files:** Platform catalogs, adapter, platform shared types, node configuration panel, comparison/export.

**Tests:** Zapier Filter vs Paths, Make binary Router, n8n IF/Switch, iterator/aggregator differences, unsupported-operation limitation, canonical graph invariance across platform changes.

**Expected output:** Distinct platform plans that never invent unsupported equivalence.

**Rollback risk:** Medium. Preserve current adapter as a fallback mapping version.

### Sprint K8 — Workflow sets and synchronized layered views

**Goal:** Support multiple independent automations per project and real Business/Automation/Developer graph projections.

**Architecture changes:** Project owns a workflow set; visual graphs are keyed per workflow; view projection uses visibility/concern metadata and graph contraction. Migrate existing projects into one-item sets.

**Files:** Domain, database, repository, APIs, editor store, workflow selector, all three views, exports.

**Tests:** Five Asana stages produce five graphs; workflow switching preserves edits; business view hides technical nodes without breaking routes; developer view shows safeguards; migration preserves IDs.

**Expected output:** Correct representation of complex scopes without one giant canvas.

**Rollback risk:** High. Use additive database fields/tables, retain legacy JSON during one migration version, and create a project snapshot before conversion.

### Sprint K9 — Branch-aware layout, real progress, and hardening

**Goal:** Make 20–40-node workflows readable and the generation pipeline observable.

**Architecture changes:** Route-aware layout metadata, loop/branch grouping, real server progress events, cancellation/timeouts, retrieval/validation/repair diagnostics, cache/version controls.

**Files:** Graph layout, editor, analysis routes/client, progress UI, performance and integration tests.

**Tests:** 20/40-node layout snapshots or geometry assertions, non-overlap, stable layout, progress stage ordering, cancellation, simultaneous Ollama queue behavior, full regression suite.

**Expected output:** Readable large workflows and truthful progress stages from analysis through rendering.

**Rollback risk:** Medium. Keep existing Dagre auto-layout and estimated progress as fallbacks.

## 14. Recommended implementation order and decision gates

1. Approve K1–K3 as the architecture foundation.
2. Run K3 retrieval in shadow mode against current real scopes.
3. Review retrieved contexts before allowing them to influence Qwen.
4. Enable K4 behind a feature flag and compare results with the current prompt.
5. Add K5 before enabling any semantic repair.
6. Require repair-report review before enabling K6 automatic persistence.
7. Upgrade platform mapping only after canonical semantics are stable.
8. Perform the high-risk multi-workflow migration after workflow-set contracts and regression fixtures are proven.
9. Finish with layout, progress, performance, and operational hardening.

## 15. Approval questions for architecture review

Before implementation, the following decisions should be approved:

1. Adopt a new `packages/knowledge` package rather than a server-only `services/workflowKnowledge` tree.
2. Use deterministic structured retrieval first; defer vector embeddings.
3. Introduce `canonicalType` additively instead of replacing `category` immediately.
4. Adopt `Project → WorkflowSet → CanonicalWorkflow[]` for multi-automation scopes.
5. Treat ambiguous missing business branches as clarification/targeted repair, not automatic compiler invention.
6. Rename the third UI layer to Developer View and render a graph projection; keep implementation notes as supporting documentation.
7. Use feature flags/shadow mode for retrieval, grounded prompting, and semantic repair during rollout.

No code implementation should begin until these decisions and the sprint order are approved.
